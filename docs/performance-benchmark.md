# Производительность Owlbear: контрольные замеры

Первый набор оптимизаций (PR #90) включает **локальные** счётчики, не синхронизируемые с комнатой.
Фоновый процесс и всплывающая панель Owlbear работают в **разных iframe**, поэтому их
статистика не объединяется автоматически.

## Как собрать показатели

1. Откройте сцену Owlbear и DevTools того iframe, который хотите измерить:
   **background** — видимость / ход / движение; **popover** — загрузка интерфейса.
2. В нужной консоли вызовите `window.__letopisPerf.reset()`.
3. Выполните сценарий 60 секунд и сохраните `console.table(window.__letopisPerf.snapshot())`.
4. Для точной CPU-картины параллельно записывайте Chrome Performance trace и смотрите
   long tasks, JS heap и частоту React commits. Счётчики `averageMs` и `p95Ms`
   включают **время ожидания SDK**, а не только JavaScript CPU.
5. Повторите сценарий на `main` и на экспериментальной ветке при тех же параметрах
   и с той же комнатой. До применения к продакшену проверьте права видимости.

## Счётчики

- `sdk.scene.getMetadata`, `sdk.scene.setMetadata` — количество и время операций
  со сценовыми метаданными.
- `sdk.scene.items.getItems`, `sdk.scene.local.getItems` — дорогие полные чтения.
- `background.movementTick`, `background.visibilityTick`, `background.turnTick`.
- `ui.loadSnapshot` — подготовка нового снимка панели.
- `sdk.scene.local.updateClonePatches` — пакетная запись частичных изменений локальных копий армий и кораблей.
- `sdk.scene.items.updateProxyPatches` — пакетная запись общих интерактивных маркеров GM.

В пакетных обновлениях используется ограничение `splitBatches` на размер/число элементов.
Для проверки эффекта сравните количество `updateItems` SDK при перемещении 30 армий
до/после: ожидается уменьшение числа отдельных вызовов, но конкретные значения
нужно подтвердить по результатам реального профилирования.
- `background.commandNotReady.sceneInitializing` — число команд, пришедших до готовности обработчика.
- `background.commandNotReady.coordinatorInactive` — число команд, для которых выбранный GM ещё не получил активные полномочия.
  У этих двух счётчиков `averageMs = 0`: они считают отказы, а не задержку.

Heartbeat обновляется **без** чтения grid/ledger/audit items и без обновления манифестов.
Проверка ревизии и действующего владельца lease остаётся обязательной.
Маршрут повторно отправляется только при явном `BACKGROUND_NOT_READY` (до 9,1 секунды ожидания);
таймауты с неизвестным результатом не повторяются автоматически.

В статистике: `calls` — число вызовов; `averageMs` — среднее; `p95Ms` —
95-й процентиль последних 128 вызовов; `maxMs` — максимум за всю сессию.
При менее 20 выборках p95 нельзя считать статистически устойчивым.

## Матрица сценариев

| Сценарий | Что проверять |
|---|---|
| Открытая сцена, 0 операций, 60 секунд | Частота полного чтения, число visibility/movement ticks |
| Одна армия меняет HP | Отсутствие повторного расчёта всей территориальной сетки |
| Переименование государства | Обновление панели и границ без ложного skip |
| 20, 50 и 100 армий | Видимость, p95 SDK, рост числа запросов |
| 30 одновременно запущенных маршрутов | Завершение всех маршрутов без задержки резервного poll |
| GM сменяет GM | Ни потерянного движения, ни двух координаторов |
| Два расширения включены одновременно | Не вызывают повторную загрузку независимо от нужды |
| 4 клиента одновременно | Согласованность снимков после действий |

## Регрессии, которые нельзя допустить

- Запуск и продолжение движения должны реагировать на реальные события scene items / metadata,
  а не ждать резервные 10 секунд.
- Устойчивое движение при сбоях соединения и передаче полномочий GM.
- Обновление несвязанных с heartbeat метаданных, в том числе grid/ledger/audit manifest
  и случаев изменения данных без увеличения `scene.revision`.
- Отсутствие утечек скрытых вражеских армий в local clones и панель игрока.
- Отсутствие дублей оверлеев при перезагрузке / переходе сцены.

## Пространственное обнаружение (square-grid broad phase)

Алгоритм `buildDetectionGraph` теперь строит пространственный индекс только если
`OBR.scene.grid.getType()` подтверждает `SQUARE`, а `getDpi()` возвращает
положительное конечное число. Для HEX/ISOMETRIC/DIMETRIC/неизвестного
типа используется прежний полный набор пар.

Пространственный индекс **не устанавливает видимость**: он лишь отбрасывает
объекты, заведомо находящиеся вне консервативной границы. Дистанция затем
измеряется штатным SDK, а видимость через преграды проверяется исходным кодом.
При изменении настроек сетки каждая новая проверка получает текущие
`getType()` и `getDpi()`, без долговременного кэша потенциально устаревших значений.

Регрессионные тесты проверяют равенство полных графов для разных режимов,
маскировки, препятствий и граничных позиций, а также сокращение количества
`distance()` при сильно рассредоточенных армиях. Для воспроизводимого
численного сравнения выполняйте `src/visibility/spatialCandidates.regression.test.ts`.
Число вызовов и время SDK на реальной карте следует измерять отдельно.

## Кэш декодированных чанков и быстрые чтения

`MetadataRepository` хранит ограниченный LRU-кэш **только декодированных**
фрагментов сетки (максимум 192 чанка на экземпляр. При чтении карты с более чем 192 чанками кэш не используется: применяется прежний полный декодер для всех чанков, чтобы избежать постоянного вытеснения (LRU thrashing)). В отличие от кэширования
всей сцены, он **не пропускает** повторную загрузку метаданных и списка объектов:
при каждом чтении по-прежнему проверяются манифест, присутствие ID всех чанков
и соответствие координат.

Повторное использование декодированного чанка возможно только при точном
совпадении текущего сериализованного содержимого и допустимой ревизии.
Изменение данных по старому ID вызывает повторную проверку и декодирование.
Недостающий/повреждённый чанк не заменяется кэшированной копией.
Возвращаемая карта всегда содержит отдельные копии изменяемых ячеек и массивов,
поэтому игровые команды не могут изменить внутренние данные кэша.
При смене сцены `invalidateOverlayCaches()` также очищает сеточный кэш.

Новые счётчики `window.__letopisPerf.snapshot()`:
- `storage.grid.chunkDecode` — количество и время фактических декодирований;
- `storage.grid.chunkCacheHit` — число успешных повторных использований (время = 0).

Проверяйте счётчики в **background** и **popover** отдельно: они работают в
разных iframe. В сценарии без изменения территории после первого чтения
число декодирований должно перестать расти, но другие SDK-чтения останутся.
Полная загрузка карты при первом входе всё ещё необходима.

Дополнительно `readFrame()` перестал повторно декодировать LR и журналы
демографии после `readItemFrame()`, а инструмент `getSceneRevision()`
читает только номер ревизии из метаданных без загрузки сетки.

Ограничение: кэш снижает локальную цену декодирования и не уменьшает размер
данных, передаваемых через Owlbear SDK. Для дальнейшего сокращения сетевых
запросов требуется отдельная, более рискованная архитектура с инкрементальными
подписками и согласованием ревизий.

## Общий снимок локальных объектов и адресные чтения

В каждом обычном `ProductionEngine.visibilityTick()` локальные копии армий,
кораблей и независимые визуальные оверлеи получают **один общий снимок**
`scene.local.getItems()`. Снимок существует только во время одного цикла
видимости и не хранится между сменами сцены, ролей или обработчиками событий.

После **однократной** очистки устаревших локальных оверлеев снимок перечитывается,
поскольку удалённые ID нельзя использовать для построения новой геометрии.
Тест проверяет, что последующий цикл видимости выполняет ровно одно чтение.

`MetadataRepository.findItem()` и диагностические инструменты могут запросить
конкретный объект через `getSceneItem(id)`, который вызывает
`sdk.scene.items.getItems([id])`. Если порт не реализует этот метод, старый
полный поиск остаётся доступен. Права и проверки ревизии при записи сохраняются.

Что измерять: `sdk.scene.local.getItems` на двух последовательных циклах,
`sdk.scene.items.getItemById` при чтении отдельного токена, а также общее время
`background.visibilityTick`. На первой загрузке число локальных чтений может
быть выше из-за миграционной очистки. Эти изменения не заменяют подписки на
обновления сцены и не разрешают кэшировать авторитетные данные команд.

## Фильтрация служебных изменений сцены

`scene.items.onChange` получает весь массив объектов при изменении сцены.
Раньше каждое изменение общих интерактивных прокси GM запускало новый
`background.visibilityTick`, `background.movementTick` и обновление popover.
Теперь оба интерфейса используют `SceneItemChangeGate`, который сравнивает
полный набор **не-служебных** объектов между соседними событиями.

Фильтр игнорирует только создаваемые расширением элементы с **единственным**
ключом метаданных `entityInteractionProxy` (тип `SHAPE`, **при точном соответствии**
исходному токену) или `mapOverlay` (тип `CURVE`). Ручное перемещение, удаление,
осиротевший или дублирующийся прокси вызывают полную синхронизацию, чтобы
восстановить кликабельность армий и кораблей. Любое изменение обычного предмета, незарегистрированного
изображения корабля, армии, корабельного маркера, преграды, чанка сетки или
объекта с неизвестными дополнительными метаданными **всегда** проходит дальше.
Первое событие после открытия сцены всегда обрабатывается. При смене сцены
сравнение сбрасывается, при некорректном/циклическом снимке или слишком
большом сериализованном содержимом фильтр пропускает все события безопасным
образом (fail-open).

Новый счётчик `scene.items.cosmeticOnlySkipped` позволяет в
`window.__letopisPerf.snapshot()` увидеть число пропущенных событий отдельно
в popover и background (показатель `averageMs = 0`, т. к. это счётчик).
Сравните в реальной сцене до/после число `background.visibilityTick`,
`ui.loadSnapshot` и количество `sdk.scene.items.getItems`.

Ограничение: это узкая фильтрация служебных событий, не полноценная
инкрементальная синхронизация армии. Она не кэширует авторитетные данные и
не пропускает изменения обычных пользовательских предметов.

## Кэш графа обнаружения (только SQUARE)

`ProductionEngine.visibilityTick()` хранит ровно один успешный результат
`buildDetectionGraph()` для **подтверждённой квадратной сетки**. Ключ
сравнения строится на основе текущих входных данных: режима обнаружения,
DPI сетки, списка и порядка армий/кораблей, сторон, позиций, дальностей
разведки, маскировки, флага игнорирования преград и геометрии всех
преград, блокирующих видимость. При изменении этих данных результат
автоматически пересчитывается.

HP, записи экономики, административная информация и другие независимые
метаданные не входят в ключ: они обрабатываются штатным путём
`visibilityTick()` на **новом снимке сцены**. Кэш касается только
графа обнаружения, а не прав доступа, отображения HP или объектов карты.
Результаты защищены копированием `Map`/`Set`, чтобы последующий код
не мог повредить сохранённый граф.

Принудительная очистка выполняется при смене сцены, смене координатора
GM, а также при `OBR.scene.grid.onChange`. Если тип сетки неизвестен
или не является `SQUARE`, измерения некорректны, объектов больше 300,
сегментов препятствий больше 2000 или сериализованные входные данные
слишком велики, используется обычный полный расчёт.
Ошибка SDK не кэшируется; результат, который завершился после
сброса кэша, не сохраняется для будущих вызовов.

Счётчики `window.__letopisPerf.snapshot()` в **background iframe**:
- `visibility.detectionGraphBuild` — число и длительность реальных построений;
- `visibility.detectionGraphCacheHit` — число повторных использований (время = 0).

Ожидаемый тестовый сценарий: при изменении только HP армии число
`visibility.detectionGraphBuild` не растёт, а при перемещении армии,
изменении дальности разведки или добавлении преграды растёт.
Важное ограничение: **все полные чтения игровых данных пока остаются**.
Повторные построения графа сокращаются, но не пропускаются сами
процедуры проверки видимости/прав и обновления локальных объектов.

Для измерений сравнивайте реальное время `background.visibilityTick` и
количество вызовов `grid.getDistance` на карте с 20, 50 и 100 армиями.
После смены сцены и передачи управления GM выполните проверку на
отсутствие видимых вражеских токенов и корректность HP-информации.

## Послойная геометрия карты

Прямоугольники рельефа и государств, а также объединённые границы могут
проходить **через несколько территориальных чанков**. Пересчёт одного чанка
без соседей потенциально даёт разрывы и изменяет ID оверлеев, поэтому
здесь выбран безопасный послойный кэш, а не приближённая нарезка границ.

`MapOverlayGeometryCache` хранит по одному результату для трёх независимых
типов геометрии:

- `terrain`: объединение клеток рельефа (только GM).
- `recognized`: прямоугольники признанного государственного контроля.
- `boundaries`: полноценные линии признанных границ и фактического контроля.

Каждая запись проверяет **точные входные данные слоя**, а не только
`gridMap.revision`. Изменение фактического контроля не перестраивает
прямоугольники рельефа и признанного контроля; изменение рельефа не
перестраивает границы; изменение государственного цвета обновляет
цвета и соответствующие границы. Для построения линий по-прежнему
используются прежние `buildStateBoundarySegmentsForFields` и
`compactBoundarySegments`, поэтому швы на границах чанков не вводятся.

Полный отпечаток рендера для обычных карт учитывает поля клеток и
показывает даже внешнюю правку, не поднявшую ревизию карты.
Для очень больших сцен, превышающих лимиты, сохраняется прежняя
схема пропуска повторных отрисовок по ревизии (во избежание
постоянной тяжёлой реконструкции). После смены сцены геометрия
и отпечатки очищаются.

Ограничения памяти: один результат на слой, максимум 10 000 клеток,
20 000 итоговых геометрических примитивов и 1 МБ сериализованного
отпечатка для каждого слоя. При превышении лимитов слой считается
заново штатным алгоритмом, без сохранения в кэше.

Новые счётчики `window.__letopisPerf.snapshot()` в background:
`map.geometry.terrainBuild`, `map.geometry.terrainHit`,
`map.geometry.recognizedBuild`, `map.geometry.recognizedHit`,
`map.geometry.boundariesBuild`, `map.geometry.boundariesHit`.
Первые отражают количество и время реальных вычислений, вторые —
число пропущенных повторных вычислений.

Проверяйте сравнением с веткой `main` при изменении рельефа,
признанных и фактических границ, DPI, цветов государств и смене
сцены. Особое внимание — участкам на стыке нескольких чанков.
